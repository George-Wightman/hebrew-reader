# Code review — 2026-08-27

A full read-through of `hebrew-reader.html` and `sw.js` as of 2026-08-27, done as a
general code review rather than in response to a specific bug report. Six bugs and
several efficiency problems found this way are already fixed — see commit `e490449`.
This document is the list of what the same pass turned up but did **not** fix, so the
next session can pick from it rather than needing to re-derive it. Findings are `G1`–`G8`,
continuing loosely from `docs/audit-2026-08-20.md`'s `F1`–`F20` but numbered separately
since this is a different pass with a different starting point.

**How to read this:** each finding has what was observed, where, and what a fix would
look like. None of these were reproduced against a live server or a real phone — they are
reasoned from the code, so verify before spending an evening on one.

## G1 · WORTH DOING · Real Hebrew audio may be one line away from working

`GEMINI_TTS_MODELS`'s own comment (hebrew-reader.html, near line 11318) records the
exact failure: every model returns `HTTP 400: "Developer instruction is not enabled for
this model"`, which is Google naming `systemInstruction` itself as the rejected field —
not the model name, not quota, not the account (both independently confirmed reachable).
The fix the comment proposes is moving the read-verbatim instruction out of
`systemInstruction` and into the `contents` prompt text instead.

This is flagged as deliberately shelved in CLAUDE.md — "George is moving to phone-first
use and asked to shelve this avenue rather than chase it further" — so it is not a
bug to fix blind. But it is testable in complete isolation, with no risk to anything
else: Settings → "Generate a test clip" spends one real TTS call and says immediately
whether it worked. If it does, every Listen / Say-it-back card starts recording real
audio from that point on, which the audit's own words are the biggest single win left
in the app.

**Where:** `geminiTTS()`, hebrew-reader.html ~11424. The `systemInstruction` field is
built at ~11433; moving its content into the `contents` prompt text (which the same
function already writes to at ~11434, "Read this aloud, verbatim: ") is the whole change.

## G2 · SERIOUS · Manual "Sync now" can run mid-drill and rewrite the card on screen

`syncRun`'s own comment states the rule: "Never mid-session: applying a merged hvr_srs
under a running drill could change the card on screen and the grade about to be written
to it." The code enforces it — `if (sessionBusy() && !opts.force) return false;` — but
the manual "Sync now" button in Settings calls `syncRun("manual", { force: true })`,
which is exactly the flag that bypasses the guard. The gear icon stays reachable
throughout a session, so pressing it and then "Sync now" mid-card is a real path, not a
theoretical one.

**Fix shape:** either grey out "Sync now" while `sessionBusy()` is true (with a note
saying why), or have `syncRun` refuse `force` specifically when a session is running and
only let `force` skip the *rate limit*, which is what the comment two lines above it
actually says the flag is for.

**Where:** hebrew-reader.html, `syncRun` ~6481–6486; the button handler is
`syncNowBtn`'s `onclick`, a few hundred lines below in the Settings wiring.

## G3 · WORTH DOING · `geminiRequest` re-probes an exhausted model every call

`aiQNote` records `"spent"` against a pool for the day once Google refuses it, and
`aiQSummary` reads that flag correctly in the Settings display. But `geminiRequest`
itself doesn't consult `aiQAll()` before trying a model — it always attempts Flash
first, waits for the 429, records `spent`, then falls through to Flash-Lite. Once the
strong pool is confirmed dead for the day, every subsequent call still pays the round
trip (and the per-minute rate-limit wait, if `waitOnRateLimit` is set) to rediscover
that.

Low cost per call, but it compounds: a busy day making many pad lookups or several
form-generation batches each eats one wasted request-and-wait before reaching the model
that would actually answer. Not a correctness bug — `aiQRecord`'s pool accounting stays
right either way — purely wasted latency.

**Fix shape:** at the top of the model loop in `geminiRequest`, check
`aiQRoll(aiQAll(), todayISO()).spent[aiPoolFor(model)]` and skip straight to the next
model if that pool is already known spent. Needs a note on why this is safe against
Google's reset not aligning to local midnight — `aiQRoll` already re-zeroes on a `today`
mismatch, so the skip only fires within the same local day the flag was set, which is
the same window the existing Settings display already trusts.

**Where:** hebrew-reader.html, `geminiRequest` ~10019, the `for (const model of ...)`
loop.

## G4 · WORTH DOING · No `fetch` in the file has a timeout

Every network call — `geminiFetchWithRetry`, `ttsFetchWithRetry`, `syncPull`,
`syncPush`, the About panel's GitHub commit check, the TTS model-list check — is a bare
`fetch()` with no `AbortController`. A connection that hangs rather than failing
outright (a flaky mobile network doing exactly that is not exotic) leaves `busy(true)`
on indefinitely: the busy ring never clears, and any `await` chain behind it — a whole
Learn session start, in the worst case — never resolves either.

**Fix shape:** a shared `fetchWithTimeout(url, opts, ms)` wrapping `AbortController`,
dropped in under the existing retry wrappers so the retry loops still see a normal
rejected promise. 15–20s feels right for the Gemini calls given they're already retried
three times with backoff; the About panel's GitHub check could be shorter since it's
non-critical.

**Where:** every `fetch(` call site — `grep -n "await fetch("` finds them all; there
are about eight.

## G5 · WORTH DOING · `trNorm` doesn't fold `ts` the way it folds `tz`

Verified live: `trNorm("tzohorayim")` → resolves in `TR_INDEX`; `trNorm("tsohorayim")`
→ does not, even though `tz` and `ts` are two spellings of the same sound George would
plausibly type either of (צהריים is genuinely written both ways). `trNorm` folds `kh`→`ch`
and `q`→`k` already, so this is the same kind of rule, just missing.

**Fix shape:** add `.replace(/ts/g, "z")` alongside the existing `.replace(/tz/g, "z")`
in `trNorm` — carefully, since `ts` is a more common substring than `tz` and could
collide with a real `t`+`s` sequence across a syllable boundary. Worth checking against
the existing `TR_INDEX` build for new collisions before shipping, the same way the
comment on `.replace(/(.)\1+/g, "$1")` already reasons about collapsing repeats.

**Where:** hebrew-reader.html, `trNorm` ~7105.

## G6 · WORTH DOING · `matchMeaning` scores on substrings, not words

Verified live: `matchMeaning("category", "cat")` returns `"good"` — a guess of
"category" is scored as matching an expected meaning of "cat", because `meaningWords`
tokenises then checks `said.indexOf(w) !== -1`, which is a substring test against the
whole joined string, not a token-set membership test. Any expected word that is a
substring of something the guesser typed will falsely match ("hurt" inside "hurts" is
probably fine and even desirable; "cat" inside "category" is not).

**Fix shape:** build a `Set` from `meaningWords(said)` and check membership
(`saidSet.has(w)`) instead of `said.indexOf(w) !== -1`. Loses nothing the current
behaviour was trying to buy — the stemming-adjacent cases like "hurt"/"hurts" were
almost certainly not what the substring check was written for, given `meaningWords`
does no actual stemming anywhere else.

**Where:** hebrew-reader.html, `matchMeaning` ~11883.

## G7 · COSMETIC · No 512×512 icon in the manifest

`manifest.webmanifest` lists only a 192×192 PNG and an SVG marked `sizes: "any"`. Most
installers accept that, but Android's install prompt and splash screen specifically look
for a 512×512 source when generating the maskable icon, and fall back to upscaling the
192 one when it's missing — which is visibly softer on a modern phone's screen density.

**Fix shape:** export a 512×512 PNG alongside the existing 192 one (the SVG source is
already in `icons/icon.svg`, so this is a re-export, not new art), add it to the
manifest's `icons` array with `purpose: "maskable"`, and add it to `sw.js`'s `SHELL`
array so it's cached for offline installs too.

**Where:** `manifest.webmanifest`, `icons/`, and `sw.js`'s `SHELL` constant near the top.

## G8 · DELIBERATE, NOT A BUG · Three audio functions still have no caller

`audioFarmRun`, `audioCoverage` and `audioClearAll` are unreferenced except by their own
definitions. This was already investigated and is recorded in the file itself
(hebrew-reader.html, ~20607): the "Build up audio library" Settings button that called
them was removed 2026-08-13 as "a live-looking control wired to a dead endpoint" — real
TTS has been broken since 08-07 (see G1) — but the functions were deliberately left in
place rather than deleted, because they become useful again the moment G1 is resolved.

Not a to-do on its own. Noted here only so a future dead-code pass doesn't remove them
without checking this note first — that would be re-doing work that was explicitly
decided against once already.

**Where:** hebrew-reader.html ~11554 (`audioJobList`, `audioCoverage`) and ~11574
(`audioFarmRun`).
